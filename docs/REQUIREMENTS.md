# AssetDesk – Requirements

AssetDesk is a web app for keeping track of a company's IT equipment: laptops, monitors, desktops and accessories. For each device it records who it is assigned to, its condition and whether it is available.

This document covers **Part 1** of the SE411 project: a React frontend whose data lives in memory. Part 2 replaces the in-memory store with a Java Spring Boot REST API (see [ARCHITECTURE.md](ARCHITECTURE.md#part-2-plan)).

## 1. Data model

| Field | Type | Rules |
|---|---|---|
| `id` | number | Generated by the service. Starts at 1 and is never reused. |
| `deviceName` | string | Required. |
| `type` | `LAPTOP` \| `MONITOR` \| `DESKTOP` \| `ACCESSORY` | Required (chosen from a list). |
| `serialNumber` | string | Required. Unique, case-insensitive. |
| `assignedTo` | string | Employee name, `''` if none. Required when status is `ASSIGNED`. |
| `condition` | `NEW` \| `GOOD` \| `FAIR` \| `DAMAGED` | Required (chosen from a list). |
| `purchaseDate` | string `YYYY-MM-DD` | Required. |
| `status` | `AVAILABLE` \| `ASSIGNED` \| `IN_REPAIR` | Required (chosen from a list). |

The UPPER_CASE codes match the Java enums planned for Part 2. The UI shows readable labels (for example `IN_REPAIR` → "In Repair").

The app starts with 12 sample assets (IDs 1–12).

## 2. Functional requirements

### Navigation
- **FR-1** A top bar shows a three-line menu (hamburger) button and the AssetDesk name and logo.
- **FR-2** A left menu links to Dashboard, Assets, Add Asset and About. The current item is highlighted. Assets stays highlighted on an asset's details and edit pages.
- **FR-3** At 900 px wide and above, the menu is pinned beside the content and the hamburger collapses or expands it.
- **FR-4** Below 900 px, the menu is a slide-over drawer with a dimmed backdrop. It closes on a backdrop click, Escape, its close button, or choosing a menu item.
- **FR-5** The hamburger's accessible name is "Open menu" or "Close menu", and it exposes `aria-expanded`.
- **FR-6** Unknown addresses show a "Page not found" page with links back into the app.

### Dashboard
- **FR-7** The dashboard shows four counters: total assets, available, assigned and in repair.
- **FR-8** It shows a horizontal bar per asset type with its count.
- **FR-9** It lists assets that need attention (status In Repair, or condition Fair or Damaged), each showing name, `ID n · serial · condition` and a status chip.

### Display assets
- **FR-10** The Assets page lists assets in a table with the columns ID, Device (name linking to details, type below), Serial number, Assigned to ("—" if empty), Condition, Purchased (for example "14 Feb 2025"), Status and Actions (edit, delete).
- **FR-11** The list is paginated, with 5, 10 or 20 rows per page. It shows "Showing a–b of n assets", Prev, page numbers and Next. Prev and Next are disabled at the ends, and the current page is marked.
- **FR-12** A "Find asset by ID" box opens that asset's details page. It shows "Enter an asset ID." when empty, "IDs are whole numbers, like 7." for non-numbers, and "No asset with ID n." when the asset doesn't exist.
- **FR-13** A "Filter by" card offers:
  - a text search on device name, serial number and employee (case-insensitive, waits about 250 ms after typing stops)
  - a Type select
  - a Condition select
  - Status pills (All, Available, Assigned, In Repair)
- **FR-14** All filters combine with AND. Any filter change returns to page 1.
- **FR-15** The filter card shows "No filters · n assets" or "k filters active · n results", plus a "Clear filters" button that is disabled when no filter is active.
- **FR-16** Filters, page and page size are kept in the URL, so refreshing the page or pressing Back keeps them.
- **FR-17** The list shows a loading state while data loads and the empty state "No assets match" when nothing matches.
- **FR-18** The details page shows every field of one asset, its status chip, and Edit and Delete buttons. An unknown ID shows a friendly not-found message.

### Add asset
- **FR-19** The Add Asset form has the fields Device name, Type, Serial number, Purchase date, Condition, Availability (status) and Assigned employee.
- **FR-20** Invalid fields get a red border and an error message under them (see section 5). The first invalid field receives focus.
- **FR-21** On success the toast "Asset added with ID n" appears, and the list opens on the page that contains the new asset.

### Update asset
- **FR-22** The Edit form is the same form as Add, prefilled with the asset's current values.
- **FR-23** On success the toast "Asset updated" appears and the details page opens.
- **FR-24** Cancel on either form returns to the previous page.

### Remove asset
- **FR-25** Delete (in the table or on the details page) opens a confirm dialog: "Delete this asset? {name} will be removed from the inventory. This can't be undone." with Cancel and a red Delete button.
- **FR-26** On success the toast "{name} deleted" appears. From the details page, the app returns to the list.

### About
- **FR-27** The About page describes AssetDesk and lists the team members (#, name, student ID). It also shows the course, university and technologies.

## 3. Non-functional requirements

- **NFR-1 Technology.** React 18 built with Vite. Plain CSS with design tokens, no UI library.
- **NFR-2 Data layer.** All data access goes through `src/services/assetService.js`. Its functions are async, return copies, and match the future REST API's routes and response shapes. Part 2 changes only this file.
- **NFR-3 Design fidelity.** The UI matches the approved mockup's layout, colours, typography (IBM Plex Sans and Mono), texts and interactions. Light and dark themes follow the system setting.
- **NFR-4 Responsive.** Works from 360 px wide upwards. Grids collapse to one column, the table scrolls sideways inside its card, and the page itself never scrolls sideways.
- **NFR-5 Accessibility.**
  - Uses real `<button>`, `<a>` and `<label>` elements.
  - Shows a visible focus ring and works with the keyboard alone.
  - Touch targets are at least 44 px.
  - Errors are linked to their fields with `aria-describedby`.
  - The dialog traps focus and returns it when it closes.
  - Toasts use `role="status"`.
- **NFR-6 Feedback.** Every action gives visible feedback: a loading state, an error message, or a toast that hides after about 2.6 s.
- **NFR-7 Quality.** `npm test` (Vitest and React Testing Library) and `npm run lint` (ESLint) pass. `npm run build` produces a production build.
- **NFR-8 No persistence in Part 1.** Data lives in memory only (no database, no localStorage). Reloading the page restores the 12 sample assets.

## 4. User stories

| ID | Screen | As a… | I want to… | So that… |
|---|---|---|---|---|
| US-1 | Menu | user | open any feature from a menu, on desktop and phone | I can move around the app quickly |
| US-2 | Dashboard | IT manager | see totals by status and type | I know the state of the inventory at a glance |
| US-3 | Dashboard | IT technician | see devices in repair or in poor condition | I know what needs attention |
| US-4 | Assets | IT staff member | browse all assets page by page | I can review the inventory |
| US-5 | Assets | IT staff member | search by name, serial or employee and filter by type, condition and status | I can find devices quickly |
| US-6 | Assets | IT staff member | jump straight to an asset by its ID | I can open a device from its asset tag |
| US-7 | Details | IT staff member | see all information about one asset | I can answer questions about it |
| US-8 | Add | IT staff member | register a new device with clear validation messages | the inventory stays complete and correct |
| US-9 | Edit | IT staff member | change an asset's details, status or assignee | the inventory reflects reality |
| US-10 | Delete | IT staff member | remove a device after confirming | retired devices don't clutter the list, and nothing is deleted by accident |
| US-11 | About | instructor | see who built the project | I can identify the team |

## 5. Validation rules

The rules are implemented once in `validateAsset()` (`src/services/validateAsset.js`). Both the form and the service use it. All strings are trimmed before checking and saving.

| Field | Rule | Message |
|---|---|---|
| Device name | required | "Device name is required." |
| Serial number | required | "Serial number is required." |
| Serial number | unique, case-insensitive (checked by the service, HTTP 409) | "An asset with this serial number already exists." |
| Purchase date | required | "Pick a purchase date." |
| Purchase date | a real `YYYY-MM-DD` date | "Enter a valid date." |
| Assigned employee | required only when status is Assigned | "Enter who this asset is assigned to." |
| Type, Condition, Status | must be one of the allowed codes | "Choose a valid type." (and similar) |

When updating an asset, the uniqueness check ignores the asset itself, so it can keep its own serial number.
